# T05 완전 통합 구현 프롬프트
## 프로젝트명: T05 Stateless Handover Lab
## 목표: Git 기반 독립 AI 세션 인수인계 및 재현성 검증

너는 Python Flask, Docker, Git, GitHub, CI/CD, 테스트 자동화, 소프트웨어 검증 및 AI 작업 인수인계에 숙련된 시니어 소프트웨어 엔지니어다.

지금부터 T05 과제 「대화가 끊겨도 이어지는 프로젝트」를 처음부터 끝까지 구현한다.

사용자는 정보통신공학 전공 4학년 학부생이며, 복잡한 서비스를 제작하기보다 T05 과제의 모든 필수 조건을 확실하게 만족하는 작고 재현 가능한 프로젝트를 원한다.

**사용자는 작업 단계마다 반복적으로 프롬프트를 입력하고 싶지 않다. 따라서 가능한 모든 로컬 구현·자동 검사·Git 커밋·문서 생성·보고를 자율적으로 수행하라.**

단, 실제 계정 인증, 원격 저장소 생성 권한, 독립 AI 세션 실행, 외부 배포 등 사용자 권한이나 별도의 실행 환경이 필요한 단계는 임의로 성공했다고 주장하지 마라.

사용자 승인이 필요한 고위험 작업과 실제로 수행할 수 없는 작업만 명확히 구분하여 요청한다.

작업을 시작한 후 오류가 발생하면 가능한 범위에서 스스로 분석·수정·재시험하고, 검증되지 않은 결과는 절대로 PASS로 기록하지 않는다.

# PART 1. 최상위 목표와 성공 조건

이번 과제는 AI 대화 기록에 의존하지 않고 Git 저장소와 표준화된 인수인계 문서만으로 개발 작업을 이어갈 수 있는지 검증하는 실습이다.

핵심 개념은 Stateless 운영이다.

Stateless는 시스템 운영 상태와 필요한 정보를 대화 기록 밖에 명시적으로 저장해, 새로운 세션에서도 동일한 작업을 재개할 수 있도록 설계하는 방식이다.

다만 실행 환경과 외부 서비스의 실제 상태까지 Git만으로 자동 보장되는 것은 아니므로, 외부 의존성과 필요한 환경변수 역시 명시한다.

검증할 전체 과정은 다음과 같다.

```
[프로젝트 초기화]
        |
        v
[고정 검사 10개 정의]
        |
        v
[Git 시작 Commit 생성]
        |
        v
[Session A 시작]
        |
        v
[Flask 기능 개선]
        |
        v
[고정 검사 10개 실행]
        |
        v
[handover.md 작성]
        |
        v
[Git Commit 및 Push]
        |
        v
[독립 Session B 시작]
        |
        v
[Git Clone + handover.md 읽기]
        |
        v
[동일 환경 재현]
        |
        v
[같은 검사 10개 재실행]
        |
        v
[Session B 잔여 작업 완료]
        |
        v
[Git Commit 및 Push]
        |
        v
[A/B 결과 블라인드 비교]
        |
        v
[최종 공개 보고서 및 제출 자료]
```

**필수 원칙**

1. Session A의 대화 기록을 Session B에 전달하지 않는다.
2. Session A와 Session B는 서로 독립된 실제 AI 세션이어야 한다.
3. 검사 10개는 구현 작업 시작 전에 고정한다.
4. A/B는 동일한 검사 정의와 기대 결과를 사용한다.
5. 검사 결과와 작업시간을 조작하지 않는다.
6. 모든 실행 환경을 저장소 문서만으로 재현할 수 있도록 한다.
7. 실제 수행하지 않은 작업은 미실행으로 기록한다.
8. Git 커밋을 작업 상태의 기준으로 사용한다.
9. 사용한 AI 서비스·모델과 실제 작업 기록을 구분해 남긴다.
10. 모든 공개 링크를 검증 가능한 HTTPS 주소로 제공한다.

# PART 3. Flask 애플리케이션 구현

## 3.1 목표

Flask API는 의도적으로 작고 단순하게 만든다.

과제의 본질은 Flask 자체가 아니라 다음을 검증하는 것이다.

- 소스코드 버전 고정
- 환경변수 기반 실행
- API 계약의 재현성
- 테스트 기준 고정
- Git 기반 작업 인수인계
- 독립 AI 세션의 재개 가능성

## 3.2 API 1 — GET /api/hello

기본 상태의 응답은 다음 구조를 따른다.

```json
{
  "message": "Hello",
  "version": "v1",
  "place": "UNKNOWN"
}
```

HTTP 상태 코드는 200이다.

Session A의 개선 작업에서는 version을 v2로 변경한다.

그리고 APP_PLACE 환경변수의 값을 동적으로 반환하도록 구현한다.

최종 목표 응답:

```json
{
  "message": "Hello",
  "version": "v2",
  "place": "DAEJEON"
}
```

APP_PLACE=DAEJEON일 때의 결과다.

APP_PLACE=SEOUL이면 place는 SEOUL로 바뀌어야 한다.

환경변수가 없다면 UNKNOWN을 사용한다.

환경변수는 Flask 앱 초기화 시점에 읽도록 구현하고, 실행 중 환경변수 변경은 재시작 후 반영된다고 명시한다.

## 3.3 API 2 — GET /api/health

정상 응답:

```json
{
  "status": "ok",
  "service": "t05-stateless-handover"
}
```

HTTP 200을 반환한다.

## 3.4 API 3 — GET /api/info

정상 응답:

```json
{
  "project": "T05 Stateless Handover Lab",
  "runtime": "Flask",
  "handover": true
}
```

HTTP 200을 반환한다.

## 3.5 정의되지 않은 API 경로

예를 들어:

`GET /api/not-found`

다음 JSON을 반환한다.

```json
{
  "error": "not_found"
}
```

HTTP 404를 반환한다.

기본 Flask HTML 오류 페이지 대신 JSON을 사용한다.

## 3.6 실행 원칙

- Flask 앱은 app factory 또는 이에 준하는 테스트 가능한 구조를 사용한다.
- 하드코딩된 비밀번호나 토큰을 사용하지 않는다.
- 환경변수를 읽지 못해도 정의된 기본값으로 실행된다.
- JSON 응답의 자료형을 고정한다.
- 서비스가 시작될 때 불필요한 외부 API를 호출하지 않는다.
- 데이터베이스와 회원가입 기능을 추가하지 않는다.
- 최소 기능 중심으로 유지한다.

# PART 4. 카드 1 — 같은 문제, 같은 검사

## 4.1 가장 중요한 원칙

기능 개선 전에 검사 10개를 먼저 정의하고 고정한다.

검사를 구현 편의에 맞춰 나중에 변경하지 않는다.

검사 항목을 정확히 10개로 유지한다.

## 4.2 고정 검사 10개

### T01 — 서비스 정상 시작

조건:
Flask 앱이 오류 없이 초기화된다.

기대:
애플리케이션 객체 생성 성공.

판정:
PASS 또는 FAIL.

### T02 — Health API 응답

요청:
GET /api/health

기대:
HTTP 200.

### T03 — Health JSON 구조

기대:

```json
{
  "status": "ok",
  "service": "t05-stateless-handover"
}
```

정확한 키와 값 및 문자열 자료형을 검증한다.

### T04 — Hello API 정상 상태

요청:
GET /api/hello

기대:
HTTP 200.

### T05 — Hello API 버전

기대:
`version` 값은 문자열 `v2`.

초기 v1 상태에서는 FAIL이 발생할 수 있다.

A 개선 작업을 통해 PASS로 전환한다.

### T06 — 기본 환경변수 처리

조건:
APP_PLACE 미설정.

기대:
`place`가 `UNKNOWN`.

### T07 — 환경변수 동적 반영

조건:
APP_PLACE=DAEJEON.

기대:
`place`가 `DAEJEON`.

기본 환경변수 테스트와 서로 영향을 주지 않도록 앱 인스턴스를 분리한다.

### T08 — 환경변수 다른 값 반영

조건:
APP_PLACE=SEOUL.

기대:
`place`가 `SEOUL`.

동일하게 독립 앱 인스턴스를 사용한다.

### T09 — Info API 계약

요청:
GET /api/info

기대:
HTTP 200과 아래 JSON 구조.

```json
{
  "project": "T05 Stateless Handover Lab",
  "runtime": "Flask",
  "handover": true
}
```

### T10 — 잘못된 API 경로 처리

요청:
GET /api/not-found

기대:
HTTP 404.

JSON 본문:

```json
{
  "error": "not_found"
}
```

## 4.3 검사 구현 방식

pytest로 각 검사 항목을 구현한다.

검사 ID와 테스트 함수가 정확히 대응하도록 한다.

예:
- test_T01_service_start
- test_T02_health_status
- ...
- test_T10_not_found

`tests/test_fixed.py`가 정확히 10개의 고정 검사 사례를 수집하도록 구성한다.

다른 보조 테스트는 별도 파일에 작성하고 고정 검사 통계에 포함하지 않는다.

테스트는 Flask test_client를 사용하며 외부 네트워크에 의존하지 않도록 한다.

단, Docker 실제 실행과 HTTP 확인은 보조 통합 검증으로 수행한다.

pytest 결과를 다음 형태로 저장한다.

```json
{
  "total": 10,
  "passed": 0,
  "failed": 0,
  "errors": 0,
  "skipped": 0,
  "results": []
}
```

실제 검사 실행 후 정확한 값을 기록한다.

검사 미실행 상태에서 total 이외의 결과를 임의로 작성하지 않는다.

## 4.4 검사 기준 불변성

고정 계약 파일:

`evidence/fixed-contract.json`

이 파일에 다음을 기록한다.

- 검사 ID
- 테스트 함수명
- 입력 조건
- 기대 결과
- 판정 방식
- 검사 정의 버전
- 고정 시점

검사 정의의 SHA256을 계산한다.

검사 파일과 고정 계약 파일의 SHA256을 함께 보존한다.

A와 B에서 해시가 동일한지 비교한다.

고정 검사 정의 파일과 구현 파일을 인수인계 이후 수정하지 않는다.

검사 결과가 실패하면 테스트를 바꾸는 대신 애플리케이션 코드를 수정한다.

## 4.5 사전 고정 절차

1. Flask 초기 v1 앱을 생성한다.
2. 검사 10개와 기대 결과를 확정한다.
3. 검사 정의 파일을 저장한다.
4. 초기 baseline 검사를 실행한다.
5. 시작 커밋을 생성한다.
6. 해당 전체 SHA를 기록한다.
7. 고정 검사 파일 수정 금지 상태로 전환한다.
8. Session A의 기능 개선을 시작한다.

초기 검사 일부가 FAIL이어도 정상적인 개발 과정으로 기록한다.

반드시 테스트를 먼저 고정한 후 기능 구현으로 개선한다.

# PART 5. 공통 시간·요청 상한

A와 B에 동일한 제한을 적용한다.

기본 제안:

- 각 AI 세션의 작업시간 상한: 90분
- 각 AI 세션의 사용자·에이전트 요청 및 도구 호출 총합 상한: 60회
- 토큰 상한: 50,000 tokens, 단 실제 측정 기능이 제공될 때만 강제
- 전체 과제 목표시간: 300분 이내

이 값은 과제 실습용 기본값이며, 외부 과제에서 강제한 숫자가 있다면 그 조건을 우선한다.

A/B의 측정 기준은 완전히 동일해야 한다.

시간은 세션 시작·종료의 실제 경과시간으로 계산한다.

가능하면 단조 증가 시계로 경과시간을 측정하고, 사람이 확인할 수 있도록 UTC ISO 8601 시작·종료 시각도 저장한다.

요청 횟수와 도구 호출 횟수를 별도 필드로 기록한다.

플랫폼이 내부 호출 수를 제공하지 않는 경우에는 관측 가능한 호출만 기록하고 전체 호출 수라고 주장하지 않는다.

토큰 사용량을 제공하지 않는 환경이라면:

`measurement_status: unavailable`

로 기록한다.

추정값을 실제 사용량으로 기록하지 않는다.

정해진 시간·요청 상한을 넘었다면 그 사실을 숨기지 않는다.

# PART 6. 카드 2 — Session A 구현

## 6.1 Session A 작업 시작

시작 정보 기록:

- 세션 이름: AI A
- 서비스: 실제 사용한 Codex 또는 AI 서비스
- 모델 표시 ID: 실제 확인 가능한 모델명
- 작업 시작 시각
- 시작 Git 전체 커밋 SHA
- 시작 커밋 HTTPS URL
- 고정 검사 SHA256
- 최초 작업 요청
- 시간·요청 상한

`docs/session-a-log.md`에 기록한다.

## 6.2 구현할 기능 개선 1개

종료:

```bash
docker compose down
```

실제 명령어가 동작하는지 가능한 범위에서 검사한다.

# PART 9. Git 및 GitHub 관리

## 9.1 Git 초기화

새 프로젝트에만 Git을 초기화한다.

기존 사용자의 Git 저장소와 설정을 변경하지 않는다.

기존 Git 자격증명이나 민감정보를 출력하지 않는다.

작업 단계별로 의미 있는 커밋을 생성한다.

예:

```
chore: initialize t05 flask baseline
test: freeze ten fixed acceptance tests
feat: implement hello v2 environment response
docs: add session a handover
test: verify independent session b
docs: publish final comparison report
```

실제 실행한 단계에 대해서만 커밋을 생성한다.

## 9.2 시작 커밋

카드 1의 검사 조건이 고정된 상태를 시작 커밋으로 삼는다.

시작 커밋은 반드시 실제 Git SHA 전체값을 기록한다.

시작 커밋 URL 예시 형식:

`https://github.com/OWNER/REPO/commit/FULL_SHA`

실제 OWNER, REPO, FULL_SHA를 조회한 뒤 사용한다.

## 9.3 원격 저장소

GitHub CLI가 인증된 환경이면 신규 공개 저장소 생성 가능 여부를 확인한다.

저장소 이름:

`t05-stateless-handover`

저장소 공개 전 다음을 확인한다.

- 비밀키 없음
- 실제 비밀번호 없음
- 개인정보 없음
- .env 실제 파일 제외
- 불필요한 로그 제외
- 토큰 출력 없음
- 기존 프로젝트 파일 포함되지 않음

원격 저장소를 만들 권한이 없거나 공개 전환에 승인이 필요하면 사용자에게 해당 단계만 요청한다.

원격 저장소가 생성되지 않았다면 가짜 GitHub URL을 작성하지 않는다.

## 9.4 소스 제출 URL

최종 URL은 기본 브랜치 URL이 아니다.

다음처럼 특정 전체 커밋을 가리켜야 한다.

`https://github.com/OWNER/REPO/tree/FULL_SHA`

FULL_SHA는 Git에서 조회한 전체 40자리 또는 64자리 소문자 커밋 해시여야 한다.

이 커밋에 최종 소스와 제출용 보고서가 실제로 포함되어 있어야 한다.

현재 Codex 실행 환경에서 다음을 확인한다.

- 독립된 새 Codex 실행을 시작할 수 있는가?
- 새 실행에 A 대화 기록이 전달되지 않는가?
- 새로운 작업 디렉터리에서 Git Clone이 가능한가?
- A와 다른 실제 모델 또는 서비스를 사용할 수 있는가?
- 각 실행의 시간 및 호출 횟수를 별도로 기록할 수 있는가?

독립 실행을 지원한다면 실제 별도 실행을 생성한다.

새 B에는 다음만 제공한다.

2. `handover.md`를 읽으라는 지시
3. A와 동일한 최초 작업 목표 및 상한

추가 정보를 전달하지 않는다.

A 세션의 비공개 로그나 대화 전문을 B에 전달하지 않는다.

독립 실행을 지원하지 않는 환경이라면 A를 종료하고 새 세션에서 사용할 프롬프트를 생성한다.

B를 실행한 척하거나 가상의 B 결과를 작성하지 않는다.

# PART 14. 과제 제출 조건

## 14.1 필수 URL

제출에는 두 개의 URL이 필요하다.

### 결과물 URL

GitHub에서 공개된 `docs/report.md`의 고정 커밋 기반 URL을 우선 사용한다.

형식:

`https://github.com/OWNER/REPO/blob/FULL_SHA/docs/report.md`

### 소스 URL

형식:

`https://github.com/OWNER/REPO/tree/FULL_SHA`

반드시 같은 최종 커밋에서 보고서와 전체 소스를 확인할 수 있도록 한다.

## 14.2 URL 접근 검증

가능한 경우 인증되지 않은 HTTP 요청으로 확인한다.

- HTTP 응답 상태
- 로그인 필요 여부
- 저장소 공개 여부
- 특정 커밋 접근 여부
- 보고서 파일 존재 여부

GitHub API 인증 성공만으로 비로그인 공개 조건을 충족했다고 판단하지 않는다.

시크릿 창 접근은 사용자에게 추가로 확인 요청할 수 있다.

## 14.3 재현·통과 확인 4가지

최종 보고서 및 출력에 아래 4개를 작성한다.

1. 위치: 실제 보고서 URL 또는 파일 경로
2. 행동: 최대 3단계의 재현 명령
3. 통과 모습: 실제 고정 검사 10개 결과
4. 안 될 때 모습: 실제 또는 정의된 실패 양상

## 14.4 AI와 내 판단 3줄

정확히 다음 형식으로 작성한다.

1. AI에게 맡긴 일:
2. 직접 판단한 일:
3. AI 제안을 따르지 않은 일:

사용자가 실제로 결정한 일만 직접 판단했다고 기록한다.

AI 제안을 실제로 거절하지 않았다면 `해당 없음` 또는 실제 변경 이유를 기록한다.

허구의 판단 과정을 생성하지 않는다.

# PART 15. A 모델 시작 기록

제출 플랫폼의 선택형 과정 기록에 사용할 자료도 준비한다.

필드:

- 서비스 표시 ID
- 모델 표시 ID
- 시간 상한(분)
- 요청 상한(회)
- 두 모델에 동일하게 줄 최초 요청
- 시작 commit URL
- 고정 검사 목록 및 기대 결과

모든 값은 실제 기록에 근거한다.

서비스 표시 ID나 모델 표시 ID는 플랫폼이 요구하는 표현과 실제 사용 정보를 우선한다.

시작 Commit URL에는 전체 SHA가 포함되어야 한다.

작성 시각을 과거로 꾸미거나 시작 기록을 소급 작성하지 않는다.

선택형 과정 기록이 제출 승인 필수 조건이라고 잘못 설명하지 않는다.
